# MarketDEX Release Process

## Release principles

Every release must be reproducible, installable, reversible, and traceable to a verified commit. The installer is the primary Windows distribution artifact; a raw executable is a diagnostic or release-candidate artifact unless the release explicitly says otherwise.

## Required release sequence

1. Confirm the exact main commit and intended semantic version.
2. Update the single version source, release notes, and changelog.
3. Run the complete applicable test suite.
4. Run formatting, lint, type, dependency, and security checks.
5. Build MarketDEX.exe from the canonical root launcher.py.
6. Run packaged runtime verification with --verify-runtime.
7. Build MarketDEX_Setup.exe with Inno Setup.
8. Install into a clean Windows user profile or test directory.
9. Verify launch, runtime database creation, uninstall behavior, and data preservation.
10. Verify required Visual North Star and mascot assets are packaged.
11. Generate SHA-256 checksums for published artifacts.
12. Publish release notes with supported Windows version, known limitations, and rollback instructions.
13. Preserve the exact commit, CI run, artifact names, checksums, and visual evidence in the repository checkpoint.

## Distribution artifacts

A normal Windows release should publish:

- MarketDEX_Setup.exe
- MarketDEX.exe as an optional portable diagnostic artifact
- SHA256SUMS.txt
- release notes
- supported-platform and known-limitations notes

## Data-protection requirements

- Never ship a user database inside the installer.
- Never delete user data during uninstall or upgrade.
- Back up before schema migration.
- Validate migration and restart reconstruction.
- Keep rollback instructions for every migration-affecting release.

## Release is blocked when

- the version is inconsistent across the app, installer, executable, and release notes;
- required tests or packaging gates are missing or skipped;
- the installer has not been tested on a clean Windows environment;
- required brand assets are missing or silently substituted;
- the release contains tracked runtime data, generated bytecode, credentials, or local build output;
- the current checkpoint does not record exact commit and CI evidence.
